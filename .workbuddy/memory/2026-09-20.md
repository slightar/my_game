## 修复两个 bug（盾兵朝向 / 按钮长按重复触发）

### Bug 1 — 盾兵攻击方向永远朝右
根因：`assets/enemies/mobs/shield_v2.png` 的攻击行（row 2）混用了两种原生朝向。
用 Pillow 逐帧算 alpha 质心（相对格子中心 96）得到：

| row | frames | 质心偏移 | 原生朝向 |
|---|---|---|---|
| 0 Idle | 0-9 | -3 ~ -5 | LEFT |
| 1 Move_Loop | 0-9 | +24 ~ +26 | RIGHT |
| 2 Attack | 0-3 | -3 ~ -12.5 | LEFT（同 Idle） |
| 2 Attack | 4-7 | +12.9 ~ +31.3 | **RIGHT（同 Move）** |
| 2 Attack | 8-9 | +0.8 / -3.1 | LEFT |

manifest 里 shield 的 `facing` 是 `[-1,1,-1,-1]`，所以 row 2 全帧按 -1（LEFT）处理，
导致左向盾兵的 Strike（frames 4-7）用了原生右向姿势 —— 盾牌挥向与 `AttackArea()`
实际命中方向相反。

修复：`src/enemy_renderer.cpp` 的 `DrawUnit` 增加 `shieldBash` 判断，把 row 2 的
frames 4-7 视为原生 RIGHT 再决定是否镜像。

### Bug 2 — 鼠标长按左键一直触发按钮
真正根因不是缺少按下反馈，而是 `src/ui_input.h` 的 `MakeUiPointer`：

```cpp
struct UiPointer { Vector2 position; bool pressed; bool released; bool down; bool valid; };
// 原代码
return {logical, pressed && valid, down && valid, released && valid, valid};
```

成员声明顺序是 `released` 在 `down` 之前，而初始化列表按 `…, down, released, …`
的顺序给值 → **down 与 released 互换**。于是 `Clicked()`（`released && Hit`）
实际变成“按住且在控件上”，长按每帧都触发。

修复：改成按名字逐个赋值。附带影响全部转正：settings 音量滑块拖拽（用 `.down`）、
地图节点选择（用 `.released`）、`game.cpp` 的 `.pressed` 都恢复本意。

另外为满足“按下变灰”的诉求，新增统一按下反馈：
- `src/terminal_ui.{h,cpp}`：`Pressed()` / `PressedVeil()`，共享灰色蒙版
  `{118,126,134,170}`；`Button()`、`Background()` 的返回键接入。
- `src/menu_views.cpp`：主页大按钮/功能块、档案条目、装备栏与条目、设置行、键位行接入。
- `src/game.{h,cpp}`：暂停菜单两个按钮也接入（新增 `Game::pointer_` 成员）。

动作仍在 release 时提交（`Clicked`），长按不再重复触发。

## 复查「大盾哥攻击时依然莫名转向右侧」

用户反馈 bug 1 未好。这次做了完整的端到端复检，结论：**源码是对的，修复有效**。

### 关键教训：之前的验证是循环论证

`bash_trace.cpp` 用「渲染后轮廓质心是否跟 `u.facing` 同侧」来判定对错 —— 但
渲染时的 `flip` 本来就是由同一份 `native` 值决定的，所以这个检查**永远会通过**，
哪怕 `native` 判断反了。判断素材朝向必须直接量**原始图集**。

### 素材朝向（逐帧实测，三种独立方法一致）

`shield_v2.png` row 2（Attack）原生朝向：

| frames | 腿/头/躯干质心 | 最大连通块质心 | 结论 |
|---|---|---|---|
| 0-3 | -3 ~ -17 | -2.9 ~ -12.2 | LEFT（与 Idle 同源） |
| 4-6 | +24 ~ +36 | +28.7 ~ +30.9 | RIGHT（与 Walk 同源） |
| 7 | +9 ~ +16 | +12.9 | RIGHT |
| 8 | ≈0（+0.5/-0.4/+1.4） | +0.9 | 中性，但连续性判为 RIGHT |
| 9 | 与 Idle f0 **完全相同** | -2.9 | LEFT（就是 Idle 姿势） |

旁证：**连续性检验**（把候选帧镜像后算相邻帧 alpha 重叠 IoU）——
3→4 关节 native 只有 0.488，镜像 frame 4 后升到 0.639，说明 frame 4 原生就是右向。
7→8 关节：8 取 native 时 0.688，8 取镜像时 0.761 → frame 8 也属右向那一组。
候选「镜像 4-9」总 IoU 最高（7.522 > 7.450 > 7.372），但 frame 9 就是 Idle 姿势，
不能镜像；故正确范围是 **4-8**。

### 代码改动

`src/enemy_renderer.cpp`：把原来 `frame>=4 && frame<=7` 的特例改成显式逐帧表
`kShieldAttackNativeRight{false,false,false,false,true,true,true,true,true,false}`，
覆盖到 frame 8，并写清实测依据。

## 咨询：AI 从「接口返回文本」升级到 agent / MCP 架构

用户问如何加入 AGI、Agent、MCP 技术栈。给出的方案（**仅讨论，尚未落代码**）：

核心判断：缺口不在模型能力，而在「把游戏状态变成模型可读写的结构化接口」。
仓库已有的 `StoryData`（纯数据）+ `ProgressSystem`（`ExitVisible/ExitAvailable/
CompleteNode/Travel/Validate` 校验链）+ `Character` JSON 严格 schema 校验，
就是工具层需要的全部材料 —— 工具只需做薄包装，且与玩家点击走**同一条代码路径**，
因此模型天然绕不过解锁条件、产生不了非法存档。

分层：表现层（已有）→ 智能体运行时（新增）→ 领域工具层（已有，包一层）→
模型与协议层（新增）。回合循环五阶段：构建上下文 → 模型提议 tool_calls →
校验执行 → 回灌结果 → 收敛或兜底。

计划暴露的工具：`get_progress` / `get_node` / `list_exits` / `suggest_route`（只读）、
`travel` / `complete_node` / `equip_item`（可写，`TerminalUi::Confirm` 确认）、
`spawn_wave`（战斗）。

五条铁律：权威状态在 C++ 侧（模型只给意图）；权限分级 + 复用确认框；
循环预算上限（≤6 步 / 8s / token 上限，超限降级到脚本对白）；
结构化输出（`tool_calls`，复用 Character JSON 的 schema 校验思路）；全异步。

MCP 双向用法：导出工具当 server → 服务 AI 自动 QA（遍历节点组合验证
`kHiddenTruthThreshold=6`、`hiddenEndingRequirements`、三个 slots 的组合）；
接入外部 server → 图像 / TTS / 知识库灌进现有导入管线。
协议 JSON-RPC 2.0，`initialize → tools/list → tools/call`，stdio 一行一 JSON。

技术选型：HTTP 用 **WinHTTP**（`-lwinhttp`，零新依赖，优于引 libcurl）；
JSON 复用已有 nlohmann/json；线程 `std::thread` + 消息队列；MCP 先 stdio，
要 HTTP 再上单头文件 cpp-httplib。

路线：P0 非阻塞 HTTP + 结构化输出（只接 `get_progress`）→ P1 ToolRegistry +
五阶段循环 + 4 个只读工具（终端透明打印每次 tool_call）→ P2 写工具 + 权限 +
确认框 → P3 持久记忆进存档 + 断网降级 → P4 MCP server 化服务 QA。

警告：**别让模型直接生成装备/技能数值**。`EquipmentModifiers` 里那个
"Replace description-only effects with typed battle modifiers" 的 TODO 是陷阱，
可以让模型提议，但必须由 C++ clamp + schema 校验落地。
